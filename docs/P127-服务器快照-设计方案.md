# P127 服务器快照设计方案（文件级回滚点 + 自适应 + 命令前拦截）

> 状态：**设计稿 v3（待评审）** · 日期：2026-10-13
> 前置：P24（OSC7 权威 PWD）、P29（分词判级）、P85（技能短路）、P122（只读门禁加固）
> 目标：**让不可逆命令变可逆** —— 在远端服务器上提供接近虚拟机快照的退路。
>
> **v3 相对 v2 的修订**（核心变化）：
> 1. **新增 §0：本方案的真正命题** —— "不可逆命令前备份，它就变可逆"。v1/v2 都在谈"快照"，没抓住这条主线。
> 2. **新增 §4：命令前拦截** —— 后端 `send_input` 行缓冲，**抢在命令执行前**判级并拍快照。
>    这是 v1/v2 最大的漏洞：v2 写的"用户改东西前自动快照"**物理上做不到**（见 §4.1 时序分析）。
> 3. **改为自适应，取消档位** —— 用户明确表示"不知道怎么选档位"。**不让用户选**，
>    由 §4.5 探测推出范围/上限/间隔/避峰。同一份代码，小 VPS 自动保守、大生产机自动激进。
> 4. **新增 §6.4：探测与执行都必须有超时** —— 实测 20000 个小文件 `tar` 需 **9.5 秒**，
>    探测本身也可能慢，且**不能阻塞用户输入**。
>
> **v2 相对 v1 的修订**（均经实测，见 §14）：
> 1. **推翻 v1 的增量方案** —— `find -newer` **看不到被删除的文件**，而"误删"正是最需要快照的场景。改为 **全量 + 变化包**模型。
> 2. **加密结论明确化** —— 见 §3.4 论证"不加密更安全"。
> 3. **敏感文件排除从"还原时"提前到"打包时"** —— 一个动作同时提升安全性与可用性。

## 0. 本方案的真正命题：让不可逆命令变可逆

**一句话**：不可逆的命令，在执行前备份一下，它就变可逆了。

这是整个功能的**唯一主线**。之前几版都在讨论"快照怎么做"（打包格式、增量策略、加密），
却忽略了**为什么需要它** —— 因为用户真正想要的不是"快照"，而是**"敢按回车"**。

### 0.1 由此推出的三个必要条件

| # | 条件 | 推导 |
|---|---|---|
| 1 | **必须抢在命令执行前** | 事后备份救不回已删的文件 |
| 2 | **必须知道要备份什么** | 全盘备份太慢；必须定位到"这条命令会动的东西" |
| 3 | **必须不打扰日常操作** | 每条命令都弹窗 = 用户会关掉功能 = 等于没有 |

v1/v2 满足了 2 和 3，**但没满足 1** —— 这是本版（v3）要解决的核心问题。

### 0.2 与"虚拟机快照"的关系

用户最初想要"类似虚拟机的快照"，并自己意识到服务器做不到。**这个判断是对的**（§1），
但**"不可逆变可逆"这个目标是可以达成的**，因为破坏是文件级的、有界的（§2）。

> 虚拟机快照给的是"随时回到任意时刻"；本方案给的是"**危险操作前自动留退路**"。
> 后者范围小得多，但**恰好覆盖用户真正在怕的事**。

## 1. 问题的本质：服务器为什么拍不了虚拟机快照

用户的原始诉求是"类似虚拟机的快照"，并自己意识到"服务器又不可能拍快照"。**这个判断是对的**，原因是缺少一层存储抽象：

| | 虚拟机快照 | 裸机服务器 |
|---|---|---|
| 磁盘形态 | 虚拟磁盘**文件**（VMDK/qcow2） | **裸块设备**，文件系统直接写 |
| 谁掌管 | Hypervisor（在客户机文件系统**之下**） | 无中间层 |
| 如何实现 | 冻结/复制磁盘文件 + CoW 位图 | 只能文件级复制 |
| 耗时 | 秒级 | 秒~分钟（取决于数据量） |

**根因**：VM 快照能"秒级、可回滚、零感知"，是因为 Hypervisor 能在**块层**暂停整个虚拟磁盘的写入。裸机上没有任何组件有权限做这件事——除非文件系统**自身**提供 CoW（LVM thin / ZFS / btrfs）。

**结论**：没有 CoW 的服务器，快照**只能是文件级 tar 打包**。本方案不假装能做到块级。

## 2. 关键洞察：对本场景，文件级够用

用户要防的不是"磁盘损坏"，而是**"手滑改错配置 / AI 执行错命令"**。这类事故的共同特征：

> **破坏是文件级的、有界的、且知道动了哪里。**

`rm -rf /etc/nginx`、改错 `sshd_config`、AI 覆盖配置——全是文件操作。文件级快照**精准覆盖这一类**。

真正需要块级的是"文件系统损坏 / 勒索加密整盘"，**那本来也不是快照能兜住的**（该靠异地备份与不可变存储）。

> **一句话**：用户想要的"VM 式安全感"里约 80% 的场景，文件级就能给，成本低两个数量级。

### 2.1 对标 VM 快照的三个爽点

| VM 爽点 | 本方案如何逼近 | 差距 |
|---|---|---|
| **秒级** | 变化包只收改动文件，常见场景 1–3 秒 | 首次全量仍慢 |
| **可回滚** | 提供还原，且**强制还原前二次快照** | 还原 `/etc` 可能锁死 SSH（见 §7） |
| **无感知** | 弹性自动触发（见 §4） | 非 CoW，写放大时仍有 IO 开销 |

## 3. 存储：位置、加密、以及"加密是否更安全"

### 3.1 `/tmp` 不可用（硬性）

CentOS 7 默认 `tmpwatch`/`systemd-tmpfiles` **10 天清理 `/tmp`**。快照放那里会**静默消失**——用户以为有退路，其实早已没有。**这比没有快照更危险。**

### 3.2 落点与权限

```
~/.helm-snapshots/                 ← 落点（非 /tmp），权限 700
├── .marker                         ← 上次快照时间戳
├── <host>-<ts>-full.tar.gz         ← 全量基线
├── <host>-<ts>-chg.tar.gz          ← 变化包（只含改动/新增）
└── index.json                      ← 快照元数据（时间/范围/大小/类型）
```

### 3.3 敏感文件排除：一个动作同时提升安全性与可用性（**v2 核心**）

**v1 把它当作"还原时的特判"，v2 改为"打包时就排除"。** 理由是一个关键观察：

> **最危险的那几个文件，恰恰是你不想还原的。**

| 文件 | 还原它的后果 | 想还原吗 |
|---|---|---|
| `/etc/ssh/ssh_host_*_key` | **换掉主机密钥 → 所有客户端报 "host key changed"** | ❌ 制造新故障 |
| `/etc/shadow` | 回滚密码哈希 | ❌ 通常不是你要的 |
| `/root/.ssh/id_*` | 回滚用户私钥 | ❌ 极少需要 |
| `/etc/nginx/*.conf` 等**配置** | 恢复正常 | ✅ **这才是要还原的** |

**实测确认**（§13 实验 4）：`--exclude='etc/shadow' --exclude='etc/ssh/ssh_host_*' --exclude='root/.ssh/id_*' --exclude='*.pem'`
→ `shadow`/`ssh_host_rsa_key`/`id_rsa` **均不在包内**，而 `nginx.conf`/`known_hosts` 正常保留。

**排除清单**（默认，可配置）：

```
etc/shadow          etc/shadow-        etc/gshadow       etc/gshadow-
etc/ssh/ssh_host_*  root/.ssh/id_*     home/*/.ssh/id_*
*.pem               *.key              *.p12  *.pfx
etc/ssl/private/*   etc/pki/private/*
```

**收益**：包内不再含密钥 → 无需加密（见 §3.4）→ 还原时也不会误换主机密钥（§7.2 的保护自然消失，少一个特判分支）。

## 4. 命令前拦截（v3 核心：真正"抢在命令执行前"）

### 4.1 v1/v2 的致命漏洞：时序上根本来不及

**v2 写的"用户改东西前自动快照"物理上做不到。** 看真实代码时序（`core.rs:702`）：

```
用户按回车
   ↓
TerminalTabs 发送 "\r"
   ↓
core.rs:702   state.ssh.send_input(&name, &data).await   ← 字节立刻写进服务器 PTY
   ↓
服务器 bash 立刻开始执行 rm -rf                          ← 此刻文件正在被删！
   ↓
（后端这时才去跑 recorder 记录）
```

**命令是"发出去就执行"，没有任何停顿。** 而 `tar` 打包 `/etc`（实测 20000 个小文件需 **9.5 秒**，见 §6.4）—— 等你拍完，文件早删完了，**拍到的是一份空目录的包**。

> **结论**：要"不可逆变可逆"，**必须把判级与备份放在 `send_input` 写 PTY 之前**。

### 4.2 拦截点选择：只有 `send_input` 同时满足两个条件

```
TerminalTabs onData ──── ❌ 拿不到完整行（Tab/↑/粘贴都会漏，P19 栽过，见 §4.3）
   ↓
core.rs send_input  ← ★ 唯一位置：字节还没进 PTY，且拿到完整字节流
   ↓
写进服务器 PTY ──────── ❌ 到这里命令已经跑起来了
```

| 方案 | 拦截时机 | 能拿到完整命令吗 | 结论 |
|---|---|---|---|
| A. 前端输入缓冲 | 回车前 | ❌ 需重建 P19 那套（会漏 Tab/历史/粘贴） | 否决（重蹈覆辙） |
| B. 服务器回显解析 | **命令已执行** | ✅ 完整准确 | 否决（来不及） |
| **C. 后端 PTY 层行缓冲** | **回车前** | ✅ 完整（后端收到全部字节） | **采用** |

**方案 C 的优势**：后端拿到的字节流**比前端更完整** —— 前端 `paste()` 绕过 `onData` 的问题不存在（粘贴也走 `sendInput`），Tab 补全的 `\t` 也在。

### 4.3 P19 的教训：输入侧解析必须处理这四类

P19 曾用 `inputBufs` 在 `onData` 里累积输入，**P23 被推翻**，因为它漏检三种输入。后端重写必须覆盖：

| 输入 | 字节形态 | 处理 |
|---|---|---|
| 退格 | `\x7f` / `\x08` | 删尾 |
| **↑ 历史回放** | `\x1b[A` | **标记本行不可信 → 放弃拦截**（见 §4.4） |
| Tab 补全 | `\t` | readline 会回显补全结果，但**输入侧看不到补全后的文本** → 本行不可信 |
| Ctrl+V 粘贴多行 | 直接 `sendInput` | 逐行处理，每行独立判级 |

### 4.4 铁律：拿不准就不拦（宁可不拦，不可错拦）

`↑` 历史回放时，前端只发 `\x1b[A`，**后端根本不知道服务器会回放哪条命令**。因此：

```
行缓冲中一旦出现 \x1b（除已知无害序列）→ 标记本行"不可信" → 不拦截，直接放行
```

**理由**：错拦的代价是"我明明按了回车却没反应"—— 这是**功能坏掉**的体验，比漏拦更糟（漏拦还有 §5 滚动基线兜底）。

**已知无害序列**（可安全忽略，不标记不可信）：
- `\x1b[3~`（Delete）、`\x1b[C`/`\x1b[D`（左右移动）、`\x1b[H`/`\x1b[F`（Home/End）
- 但为**降低风险**，v3 首版实现**一律标记不可信**，只保留退格/回车/可见字符的处理。

### 4.5 拦截决策流

```
send_input(name, data)
   ↓
追加进该会话行缓冲（处理 \x7f 退格、\r 结束、\x1b 标记不可信）
   ↓
遇到 \r  →  得到完整命令行 cmd
   ↓
untrusted?  ── 是 → 原样发送（不拦）
   ↓ 否
check_danger(cmd)  ← 复用 safety.rs（P29/P122 两轮加固）
   ↓
┌─ Critical  →  不发送！弹确认：
│                 [先拍快照再执行]  [直接执行]  [取消]
│                 选拍 → tar 打包 → 校验 → 再发送
│
├─ Warning   →  按自适应策略（§4.6）：默认只记录不拦
│
└─ Safe      →  原样发送，零延迟
```

**判级是纯字符串运算（微秒级），不拍快照时延迟可忽略。**

### 4.6 为什么不能只靠 Critical：两层判据

`check_danger` 的 Critical 是**系统级**危险（`rm -rf /`、`shutdown`、`mkfs`）。但**改坏 nginx.conf 的 `sed -i` 是 Safe** —— 后果一样严重。

因此两层：

| 层 | 判据 | 拦什么 | 效果 |
|---|---|---|---|
| **拦截层** | `check_danger == Critical` | `rm -rf /etc` 这类不可逆 | **零丢失**（抢在命令前） |
| **基线层** | `is_readonly_command == false` | 所有写操作 | 最多丢 T 分钟（见 §5） |

**基线层逻辑**：首次写操作**立即拍**（建立基线），之后每 N 条写操作 / T 分钟更新。
这样 `sed -i` 改坏了，退路是最近的基线。

### 4.7 弹窗频率是成败关键

**如果每条写命令都弹，用户会烦到直接关掉功能 = 等于没有。** 所以：

- **只对 Critical 弹**（这类命令日常很少）
- Warning 默认**只记录不拦**（自适应可升级，见 §4.8）
- 日常修改**完全静默**，靠滚动基线兜底

### 4.8 自适应：不让用户选档位

用户明确表示"**不知道怎么选档位**"。这本身就是设计错误的信号 —— 如果连作者都不知道选哪个，用户更不知道。

**修法：不让用户选，由探测推出参数，以"结论"形式告知。**

```
探测（连接时一次）：df + du -sb <候选路径> + 复用已有 loadavg/mem_total
   ↓
自动推出：范围 / 上限 / 间隔 / 拦截级别 / 是否避峰
   ↓
告知用户（不是选择题，是结论）：
   "已按本机情况配置：快照 /etc（约 6MB/次），保留 10 份，共约 60MB。
    当前磁盘可用 2.1GB。如需调整可展开。"
```

**同一份代码，两种服务器自动分化**：

| | 小 VPS | 大生产机 |
|---|---|---|
| 探测到 | `/etc` 18MB、盘余 2GB、内存 2GB | `/etc` 200MB、`/home` 40GB、盘余 500GB |
| 自动范围 | `/etc` | `/etc` + `/usr/local` + `/opt`（**自动排除 `/home`**） |
| 自动上限 | 100MB | 2GB |
| 自动间隔 | 30 分钟 | 5 分钟 |
| 自动避峰 | 不需要 | load > 核数×0.7 时**推迟** |
| 拦截级别 | Critical | Critical（可选升到 Warning） |

**关键**：大机器"自动排除 `/home`"是**推出来的**，不需要用户懂 —— 因为 `/home` 通常是业务数据（另有备份），而 `/etc` 才是"改错了要还原"的东西。

**换机器时重新探测** → 参数自动跟着变。

### 4.9 探测数据来源（大部分已有）

| 信号 | 来源 | 决定 |
|---|---|---|
| 磁盘可用 | `df`（**新增**） | 上限 |
| 目标路径体积 | `du -sb`（**新增**，带超时） | 范围 |
| 负载 | `load1/5/15`（**`monitor.rs` 已有，2 秒一次**） | 避峰 |
| 内存 | `mem_total_mb`（**已有**） | 机器规模判定 |

### 4.10 能力探测：实测结果（2026-10-13，测试机 192.168.132.130）

**这一节是实测数据，不再是推测。** 结论直接改变方案：**这台机器上只有 tar 可用**。

| 探测项 | 实测值 | 结论 |
|---|---|---|
| 系统 | CentOS 7.9.2009，内核 3.10.0-1160 | — |
| 根分区 | `/dev/mapper/centos-root`，**XFS**，17G（用 5G） | — |
| 磁盘布局 | `sda` 20G → `sda2` 19G **LVM** → `centos-root` + `centos-swap` | 在 LVM 上 |
| **LVM 剩余空间** | **`vg_free = 0`，`free_count = 0`** | ❌ **LVM 快照不可用** |
| **reflink** | `cp --reflink=always` **失败** | ❌ **不可用**（CentOS 7 的 XFS 默认 `reflink=0`） |
| `xfs_info` | 命令不存在（xfsprogs 未装全） | 探测需容错 |
| overlayfs | `/proc/filesystems` 有 | 但已运行系统插不进（§1） |
| **tar** | **GNU tar 1.26** | ✅ |
| tar 关键选项 | `--exclude` ✓ / `--newer-mtime` ✓ / `--one-file-system` ✓ | ✅ 全支持 |
| **`/tmp` 清理** | `systemd-tmpfiles-clean.timer` **static**，`/tmp` 默认 **10d** | ⚠️ **确认 `/tmp` 不能用**（§3.1） |
| `/etc` 规模 | **36M / 1732 文件** | 打包 **<1 秒** |
| `/root` 规模 | 832M | 偏大，默认不必全收 |

**三条决定性推论**：

1. **LVM 快照在这类机器上普遍不可用** —— 磁盘 20G 全部分配完（root 17G + swap 2G），
   这是**多数 VM 装系统时的默认状态**。要腾空间只能缩容，而 **XFS 不支持缩小**（只能扩）
   → 除非重装或加盘，LVM 快照永远用不了。
2. **reflink 也不可用** —— `reflink` 是 RHEL 8 时代才默认开启的；CentOS 7 的 `mkfs.xfs 4.5.0` 默认关闭。
3. **tar 是唯一可行机制**，且**够用**：`/etc` 仅 36M/1732 文件，打包 <1 秒。

> **这恰好验证了 §4.8「弹性降级」的必要性**：若硬编码"用 LVM 快照"，这台机器直接不可用；
> 而弹性设计会**自动降级到 tar**，功能照常工作。

**探测命令必须容错**：`xfs_info` 不存在、`vgs` 无输出、`cp --reflink` 失败 ——
每一条都要按"不可用"处理而不是报错中断。

## 5. 滚动基线（拦截层的兜底）

拦截层只挡 Critical，`sed -i` 这类改配置的命令**拦不住也不该拦**（太频繁）。退路靠滚动基线：

```
首次写操作（is_readonly_command == false）  →  立即拍基线
之后每 N 条写操作 或 T 分钟                  →  更新
手滑改坏配置                                →  退路 = 最近一次基线（最多丢 T 分钟）
```

**为什么"首次写操作立即拍"**：否则"用户改了 10 个文件后才拍"，前 9 个文件的原始状态已永久丢失。

**为什么用 `is_readonly_command` 而不是命令条数**（用户明确要求"弹性"）：

> 用户原话："这个肯定要是弹性的，如果都是查询肯定没必要。"

`src-tauri/src/safety.rs` 的 **`is_readonly_command`**（P122 刚加固）就是现成判据：
- **77 个白名单命令** + 每命令的**参数守卫**（`guard_ok`）
- 额外拦截：重定向 `>`/`<`、命令替换 `$()`/反引号、后台 `&`
- 白名单外**保守视为写操作**

于是：50 条 `ls`/`grep`/`tail` **一次都不拍**；3 条 `sed -i` **会拍**。

### 5.1 触发通道：OSC7 提示符（复用 P24）

| | OSC7 提示符 | 解析输入字节流 |
|---|---|---|
| 语义 | **一条命令执行完毕** | 用户敲了什么（含退格/方向键/Tab） |
| 可靠性 | 高（bash 每次重画提示符都发） | 低 |
| 已有基础 | **P24 已做成权威 PWD 通道** | `recorder.rs` 有解析但仅供记录 |
| 局限 | 依赖 bash | 无 |

> 非 bash 会话（`kind != linux` 或无 OSC7 标记）**不启用自动基线**，只保留手动与拦截——宁可不自动，不可乱自动。

---

### 3.4 加密：**不加密更安全**（v2 论证）

用户的直觉是"加密更安全"，但**这里是反的**。三个层次：

**(a) 加密防的是冗余威胁。**
谁能读 `~/.helm-snapshots/`？只有 root（权限 700）。而**有 root 的人能直接读 `/etc/shadow`，根本不需要你的快照**。加密防的是一个已被挡住的攻击路径。

**(b) 加密的代价直击快照的唯一目的。**

| | 不加密 | 加密 |
|---|---|---|
| 密钥丢了 | 不存在这问题 | **快照全废** |
| 换电脑/重装 | 不受影响 | **DPAPI 密文全部解不开** |
| 取回单个文件 | 直接解包 | 必须解密全包 |
| 灾难时可用性 | 只要文件在就能还原 | **还要额外满足"密钥还在"** |

> **已实测确认**：`crypto.rs` 注释写明 DPAPI"同机同用户可解密；**换机器或换账户后需重新填写**"（P13/P26 既有语义）。

**(c) 真正该加密的是"离开服务器的副本"。**

判断标准只有一条：

> **快照会不会离开这台服务器？**
> - **不会** → **不加密**（本方案默认）
> - **会**（拉回本机 / 上传云 / 被备份任务同步）→ **加密**，且必须解决密钥托管

**结论**：v2 把加密从"默认关"升级为**唯一推荐路径是不加密**，仅当副本离开服务器时才提供加密，且开启时**强制选择密钥托管方式**（自持口令 / 本机 DPAPI / 不加密），不给"随便存"这个选项。

## 6. 快照范围：由"事实"决定，不由"清单"决定

用户对范围"还没想好"——**这恰恰说明不该用预设清单**（任何"关键路径"清单都不全，且随业务变化过期）。

### 6.1 两种触发原因，两种范围

| 触发原因 | 范围 | 依据 |
|---|---|---|
| **AI 要跑危险命令** | 从命令中**解析出的目标路径** | `safety.rs` 的 `tokenize_segment` 已分词 |
| **用户自己改东西** | 扫描范围内的**实际变化** | 与基线对比（见 §5.3） |

### 6.2 解析失败时必须拒绝，不能猜

Agent 场景下若从命令里解析不出目标路径（如 `bash -c "$(cat x)"`）：

> **拒绝自动快照，并明确告知用户"无法确定影响范围，请手动指定或先手动拍一次"。**

**理由**：猜错路径 → 打了一份无关的包 → 用户以为有退路 → 实际没有。**这比不拍更危险。**

### 6.3 打包模型：**全量 + 变化包**（v2 推翻 v1 的增量方案）

**v1 的错误**（实测确认，§13 实验 2）：用 `find -newer <marker>` 收集变化 → **被删除的文件永远看不到**（文件已不存在，`LastWriteTime` 无从谈起）→ **增量包无法恢复误删文件** → 而误删正是最需要快照的场景。

**v2 方案**：

```
第一次：tar -czf <host>-<ts>-full.tar.gz  <scan_paths>   ← 全量基线
之后：  tar -czf <host>-<ts>-chg.tar.gz   --newer-mtime=<上次时间> <scan_paths>
```

**还原 = 解全量 + 依次解变化包**（实测通过，§13 实验 3：被删的 `app.conf` 从全量包完整恢复为 `keep-ORIGINAL`）。

**为什么不用 GNU tar 的 `--listed-incremental`**（实测否决，§13 实验 1）：
- 删除信息编码在**目录条目**上，还原顺序敏感
- **不支持"只还原到某个时间点"**（它是一条链，必须从头解到尾）
- Windows 侧 GNU tar 还原实测失败（`Cannot connect to C:` 是路径歧义，但也暴露了跨平台脆弱性）

**代价**：变化包需与全量包配套。用 `index.json` 记录依赖关系，UI 展示为"快照链"。

### 6.4 扫描范围白名单

```
/etc /root /home /usr/local /opt /srv /var/www
```

**明确跳过**：`/proc /sys /dev /run /tmp /var/lib /var/cache /var/log`（大且无意义，`/var/log` 另有轮转）。

`--one-file-system` 防止跨挂载点（避免把挂载的 NFS/数据盘卷进来）。

### 6.5 探测与执行都必须有超时（v3 新增，实测依据）

**实测**（§14 实验 5）：`/etc` 这种"小文件极多"的目录，**20000 个文件 `tar` 需 9467 ms**。

两个直接推论：

| 环节 | 风险 | 处理 |
|---|---|---|
| **探测**（`du -sb`） | 大机器上扫 `/home` 可能几十秒 | **硬超时 5 秒**；超时即判定"该路径过大" → **不纳入范围** |
| **打包**（`tar`） | `/etc` 就可能 10 秒 | 硬超时（默认 120 秒）；超时 → **中止并删除残包** |
| **拦截等待** | 用户按了回车在等 | 必须**显示进度**（"正在拍快照 3/10 秒…"），且**可取消**（取消 = 放弃快照、直接执行） |

**关键**：探测与打包都跑在**独立 exec 通道**（复用 `monitor.rs` 的 `exec_handle` 模式），
**不占用交互 PTY**，因此不会阻塞用户在终端里的其他操作。

## 7. 空间与体积前置检查

### 7.1 防"打包撑爆磁盘"（最容易翻车处）

> `/` 剩 2% 时 `tar czf` 写到一半撑爆磁盘 → **可能连带搞坏正在运行的服务**（日志写不进、数据库无法提交）。

**必须的前置顺序**：

```
1. df 落点所在分区       → 可用空间 A
2. du -sb 待打包路径      → 预估原始体积 B
3. 预估压缩后 ≈ B × 0.3（配置文本压缩率高）
4. 若 A < 预估 × 3（安全系数）→ 拒绝执行并说明具体数字
```

**绝不"尽力而为"地硬上**——磁盘写满的连带损害远大于"这次没拍成"。

### 7.2 体积上限

默认 `max_size_mb = 500`，超出则拒绝并提示缩小范围。
（依据：配置文本压缩率通常 5:1~10:1，500MB 压缩后约 50–100MB，对常见 VM 磁盘余量安全。）

### 7.3 保留策略

`keep = 10`，超出删最旧。**删除时必须连它的变化包一起删**（否则链断，全量没了变化包也无意义）。

## 8. 还原（最后做，且最危险）

### 8.1 铁律：还原前强制二次快照

还原会覆盖**当前正在使用的配置**。若还原后发现"新配置也有问题"，**原始状态已永久丢失**——还原本身成了不可逆操作。

> **"还原前先对当前状态再拍一次"硬编码进去，不提供关闭开关。**

### 8.2 SSH 锁死风险（v2 已因 §3.3 大幅降低）

**v1 的方案是"还原时排除 `/etc/ssh`"；v2 因为打包时就已排除主机密钥，风险面显著缩小。** 但仍需处理：

- `/etc/ssh/sshd_config` **本身**（不是密钥）仍会被打包 → 还原错误配置可能导致 `sshd` 起不来
- 处理：还原后自动 `sshd -t` 语法校验，失败则**不 reload**，保持原状并告警

### 8.3 还原必须可预演

还原前展示 **diff 清单**：哪些文件将被覆盖、哪些新增、哪些会被删除。用户确认后才执行。

### 8.4 还原到原路径 vs 还原到临时目录

提供两种模式（默认后者更安全）：

| 模式 | 说明 |
|---|---|
| **预演/暂存**（默认） | 解到 `/tmp/helm-restore-<ts>/`，用户自行对比后再手动覆盖 |
| **就地还原** | 直接覆盖原路径，需二次确认 + 强制二次快照 |

## 9. 配置项

照 `AiConfig` 既有模式（`agent_confirm`/`agent_fc`/`ai_echo_terminal` 先例）。

**关键设计：区分「用户可调」与「探测自动填充」** —— 后者不暴露在设置页，避免让用户做他不知道怎么做的选择（§4.8）。

```rust
pub struct SnapshotConfig {
    // ---- 用户可调（设置页可见）----
    pub enabled: bool,                 // 默认 false（会写服务器磁盘，必须显式开启）
    pub dir: String,                   // 默认 ~/.helm-snapshots
    pub keep: u32,                     // 默认 10
    pub intercept_critical: bool,      // 默认 true：Critical 命令前弹确认
    pub restore_dir_mode: bool,        // true=暂存目录（默认）
    pub encrypt: bool,                 // 默认 false（见 §3.4）

    // ---- 探测自动填充（设置页折叠为「高级」，只读展示 + 可覆盖）----
    pub probe: Option<ProbeResult>,    // 连接时探测一次，换会话重探
    pub scan_paths: Vec<String>,       // 由 probe 推出，见 §4.8
    pub exclude: Vec<String>,          // 默认见 §3.3
    pub max_size_mb: u64,              // 由 probe.disk_avail 推出
    pub auto_after_writes: u32,        // 由 probe 推出（小机 5 / 大机 3）
    pub auto_min_interval_mins: u32,   // 由 probe 推出（小机 30 / 大机 5）
    pub avoid_load_ratio: f64,         // 默认 0.7：load > 核数×0.7 时推迟（§4.8）
    pub probe_timeout_secs: u64,       // 默认 5（§6.5）
    pub pack_timeout_secs: u64,        // 默认 120（§6.5）
}

/// 连接时探测一次的结果（决定上面那组自动参数）
pub struct ProbeResult {
    pub disk_avail_mb: u64,            // df 落点分区
    pub path_sizes: Vec<(String, u64)>, // du -sb 各候选路径（带超时）
    pub mem_total_mb: u64,             // 复用 monitor.rs
    pub cpu_cores: u32,
    pub load1: f64,                    // 复用 monitor.rs
    pub probed_at: u64,
}
```

## 11. 分期建议（v3 调整：拦截提前到二期）

| 期 | 内容 | 风险 | 可独立验证 |
|---|---|---|---|
| **一期** | 探测 + 手动快照：全量打包 + 排除清单 + 空间检查 + 列表 + 保留策略 | 低 | 是（真机跑） |
| **二期** | **命令前拦截**（§4）：后端行缓冲 + `check_danger` + 确认卡 | 中 | 是（造 `rm -rf` 场景） |
| **三期** | 滚动基线（§5）：OSC7 计数 + `is_readonly_command` 过滤 | 中 | 是（造写操作场景） |
| **四期** | 变化包 + 快照链 + 单文件取回 | 低 | 是 |
| **五期** | 还原（暂存模式 → 就地模式，含二次快照 + diff 预演 + `sshd -t`） | **高** | 需谨慎设计测试 |

**为什么拦截（二期）要早于基线（三期）**：拦截才是"不可逆变可逆"的**主路径**（零丢失），
基线只是兜底（最多丢 T 分钟）。主路径先做，价值立刻可见。

**一期必须先做完并真机验证** —— 拦截弹窗要等 1~10 秒，得先有个可靠的打包底座。

## 12. 明确不做的事（边界）

| 不做 | 理由 |
|---|---|
| 块级/CoW 快照 | 依赖服务器存储栈，多数 VM 未配；可作为**能力探测提示**，不实现 |
| 整盘/整机备份 | 那是备份软件的领域；本方案定位是"改动前的回滚点" |
| 跨服务器统一快照 | 复杂度爆炸，与"单会话上下文"架构不符 |
| 默认加密 | 见 §3.4：加密把可用性问题变成密钥可用性问题 |
| 自动还原 | 还原永远需要人确认 |
| `--listed-incremental` | 见 §6.3：不支持时间点还原，且跨平台脆弱 |
| **让用户选档位** | 见 §4.8：用户明确表示"不知道怎么选" → 改为探测自动推出 |
| **拦截非 bash 会话** | 无 OSC7 与可靠行缓冲，错拦风险高（§4.4 铁律） |

## 14. 实测记录（历次修订的依据）

全部在本机 Windows + Git 自带 GNU tar 1.35 上验证（目标平台是 Linux，机制相同）。

| # | 实验 | 结果 | 结论 |
|---|---|---|---|
| 1 | `tar --listed-incremental` 增量+还原 | 删除信息在目录条目上；**还原后 `app.conf` 未恢复**、`nginx.conf` 未更新 | **否决该方案**：不支持时间点还原 |
| 2 | `find -newer` 能否发现删除 | **被删文件完全不出现** | **推翻 v1 增量方案** |
| 3 | **全量 + `--newer-mtime` 变化包** | 解全量+变化包 → 被删的 `app.conf` **完整恢复为 `keep-ORIGINAL`**，改动与新增均正确 | **采用此方案** |
| 4 | `--exclude` 排除敏感文件 | `shadow`/`ssh_host_rsa_key`/`id_rsa` **均不在包内**；`nginx.conf`/`known_hosts` 正常保留 | 排除清单有效 |
| 5 | **20000 个小文件的 `tar` 耗时** | **9467 ms**（包 20MB）；同目录枚举 374 ms | **v3 新增超时设计的依据**（§6.5） |
| 6 | 截断的 tar 包能否检测 | `tar -t` 与 `tar -x` **均返回 exit=2**（`Unexpected EOF`） | 打包后**必须校验**，残包要删（§7.4） |

**踩到的三个环境坑**（记下以免复现）：
- Windows 自带 `tar.exe` 是 **bsdtar**，不支持 `--listed-incremental`（用 Git 的 GNU tar 测）
- Git 环境**缺 gzip**，`-czf` 直接失败 → 验证用 `-cf` 不压缩
- GNU tar 把 `C:\...` 误解析为 `host:path`（`Cannot connect to C:`）→ 测试用相对路径

### 14.1 由实测推出的两条硬性要求（v3 新增）

**(a) 打包后必须校验，残包必须删**

实验 6 证明截断包**可被检测**（exit=2）。但方案里必须有明确动作：

```
tar 打包 → tar -tzf 包 > /dev/null 校验
   ├─ exit=0 → 写入 index.json，标记可用
   └─ exit≠0 → **立即删除残包**，并在 UI 明确报错
```

**理由**：**残包比没有包更危险** —— 用户以为有退路，实际还原时才发现是坏的。

**(b) 必须有"验证快照可用性"的操作**

用户怎么知道快照真能还原？**没有验证机制的快照就是信仰。**

```
验证 = 解包到临时目录 → 比对文件数与 index.json 记录
   → 通过：标记 ✓ 已验证
   → 失败：标记 ⚠ 损坏，建议重拍
```

建议**每次打包后自动跑一次轻量校验**（`tar -tzf` 计数即可，不解全包），
并提供手动"完整验证"（真解包，慢但彻底）。
